## Prototype review

The prototype `minter-contract/contracts/anlgram-f02-receipt-prototype.fc` receives `0x7362d09c` and authenticates the message sender against the deterministic **recipient** LP wallet; it checks the encoded provider, query ID and tag. TON's [Jetton processing guide](https://docs.ton.org/applications/payments/jettons) confirms the recipient wallet sends `transfer_notification` and that wallet identity must be authenticated. The LP master is the derived Pool; `stonfi-v22-auth.fc` derives its StateInit using pinned development-profile code, pair ordering and fees, and then derives the recipient wallet. This derivation alone does not prove live Router code, wallet-master bindings, upgrades, or configuration trust.

The immutable StateInit includes the operation ID and configuration, but uniqueness is only for the entire input tuple: the same tuple recreates the same address, and no global operation-ID registry exists. The constructor has no independent zero-initial-balance check, so callers must authenticate the exact intended initial state. The code records the first positive matching notification, rejects later notifications, and contains no explicit outgoing send actions; rejected bounceable messages can still produce protocol-level bounces. The test checks the wallet balance once off-chain after a successful local provision; the contract does not check its current balance. A real transfer by the configured provider with the same query and tag could satisfy the same receipt checks; the receipt does not itself establish a mint, consumption of either leg, or closure. Rejected later notifications do not reverse actual wallet credits.

If deployed and funded, this contract has no withdrawal or forwarding path and LP held in its wallet is inaccessible through the owner. This is a **deployment blocker**, not a demonstrated production exploit: the PR labels it sandbox-only and no financial integration was found in the reviewed source; deployment state was not checked. Likewise, treating a matching notification as settlement would be a serious conditional integration error, but no current production consumer was found. Neither conditional issue is assigned a vulnerability severity without a demonstrated production boundary violation.

## Architecture comparison

| Option | Supported semantics and guarantees | Open assumptions, recovery and custody risks | Automatic terminal settlement |
|---|---|---|---|
| A: unique per-operation depositor and authenticated wallets | Separates provider identities and can limit which assets each escrow controls; authenticated receipts and immediate bounces can account for assets actually received. | A unique address is not a message fence. LPAccount can be recreated within the same operation; refund, late delivery and downstream wallet failure remain asynchronous. Escrow and gas introduce additional custody and upgrade risks. | Not established on reviewed STON.fi interfaces. |
| B: supported STON.fi extension | Router has `provide_lp` parameters, including recipient and custom payload; LPAccount has query and refund operations. | Reviewed [Router](https://docs.ston.fi/developer-section/dex/smart-contracts/v2/router), [Pool](https://docs.ston.fi/developer-section/dex/smart-contracts/v2/pool), and [LPAccount](https://docs.ston.fi/developer-section/dex/smart-contracts/v2/lpaccount) documentation does not specify an operation-bound terminal receipt with both asset partitions and message closure. An extension would require actual supported code, version pins and review. | Not demonstrated. |
| C: isolated escrow, pending states and externally verified reconciliation | Can make custody and conservative operation states explicit, with authenticated owner actions bounded by actual holdings and exact liabilities. | External reconciliation changes the trust model. A signer, timeout, empty account or LP receipt cannot supply a cryptographic message-closure guarantee. Recovery cannot spend assets still held by foreign contracts and must tolerate delayed messages and repeated requests. | Only under explicitly accepted external trust; it is not proof under the original acceptance criterion. |
| D: alternative TON DEX, e.g. DeDust | Its [liquidity documentation](https://docs.dedust.io/docs/liquidity-provisioning) and [TL-B reference](https://docs.dedust.io/reference/tlb-schemes) describe asset vaults, a liquidity-deposit contract, cancellation, and payloads. | Payload/event semantics, failure and delayed-leg behavior need source, bytecode and adversarial verification. Its external event is not automatically an on-chain terminal receipt. Switching introduces migration, liquidity and custody risks. | Unproven; do not assume a different DEX closes the gap. |

## Recommendation and work remaining

Keep 414 closed and do not wire the observer into the financial pipeline. Research a one-operation escrow with dedicated asset identities as a containment mechanism, while recording unresolved liabilities indefinitely and defining any externally authorized recovery as a separate, explicit trust model. In parallel, establish whether STON.fi will support an operation-bound terminal interface or whether a feasible contract-verifiable proof of finalized TON history can cover every descendant message, final asset partition, code identity and closure. [TON's proofs overview](https://docs.ton.org/foundations/proofs/overview) supports research into inclusion proofs; it does not supply this complete settlement proof.

Before any activation, run the existing baseline and new adversarial traces in an OS-isolated offline environment; record compute/action results, account and wallet balances, in-flight messages, and source/bytecode hashes. Independently test delayed deposits, account recreation, stale evidence, partial returns, LP delivery failure and action-phase failures across both orders. Prove a specific recovery design against late messages, complete Curve/Locker V3 integration and obtain independent security review. Do not describe external attestation as on-chain proof. No automated completion should be claimed until the original conservation and closure criteria are actually demonstrated.
