## Implemented scope and compatibility

- New **separately named** Guard, Curve and Migrator sources and artifacts. Existing V1/V2 contracts, minter, settlement wallet and Locker V2 artifacts remain byte-for-byte unchanged. Do not replace any deployed contract with these files.
- Guard verifies Ed25519 permissions for phase 1 (graduated Curve pre-dispatch) and phase 2 (funded Migrator registration). Fields bind actual Testnet global ID `-3`, exact Guard/Curve/Migrator/master, project-specific LP intent, root operation, reserve obligations, three epochs, minimum LP, nonce, version commitment and a window no longer than 60 seconds.
- Network is checked against TVM configuration 19, not only a caller-supplied field. Mainnet is rejected. Public authority key is an explicit nonzero genesis input; no default key, key rotation, signing service, withdrawal authority or admin upgrade path was added.
- The Curve's source-checked graduation conditions remain 500 TON, no unsettled token claims, zero curve inventory and exactly 200M DEX units at nine decimals. Existing supply is 1 billion, allocation 80/20, fee 1%; VNext rejects a mutated fee field rather than silently overwriting it. Donation and production configuration were not modified.
- Acyclic identity binding: the Guard commits to the complete Migrator StateInit with **only its Guard address normalized to addr_none**. After deriving the Guard, derive the real Migrator and Locker. The Curve validates both StateInits, code pins, authority configuration and LP intent, then sends a one-time authenticated binding to Guard. Different genesis contents cannot be substituted. The same funded binding can be retried after a failed initial delivery; it moves operational gas only.
- Version commitment covers Guard, Migrator, Locker V2 and settlement wallet code plus protocol version; exact Curve code is pinned by this artifact package and its StateInit/address is bound in each permission. There is no circular self-hash commitment.
- Registration uses the existing reserved record location. Staged permissions can renew only after expiry with nonce + 1. A granted permission requires an expired, authenticated safe-phase revocation from the exact Curve/Migrator before renewal. Both consumers check their actual local epochs and obligations. Lost responses can be queried again with the same digest; this re-emits permission, **not assets**. Old nonce/digest and legacy approval callbacks are rejected.
- Migrator wallet initialization must match the immutable Locker LP wallet and intent pTON wallet, after vault binding. Execution validates the same wallets and permission. Authorization is in a reference cell: putting three addresses plus its digest in the root exceeded the 1023-bit cell limit in the initial local test and was corrected.
- Curve dispatch and Migrator execution still reject with **414** after permission checks. Finalization remains blocked. Enabling them requires a separately reviewed settlement design, not deletion of a denial or approval of a signature.

The actual message/code dependency chain is: unchanged project minter and settlement wallet -> VNext Curve -> VNext Guard(template commitment) -> VNext Migrator -> unchanged Locker V2 -> pinned STON.fi Router/Pool/LPAccount/LP wallet and pTON. The offline factory reuses existing metadata, LP terms and deterministic derivation helpers. No live VNext project/operator manifest or authority key has been configured.

The new Curve initialization has a fourth StateInit reference (Guard). Pre-dispatch now includes nonce/digest; Migrator execution includes an authorization reference; Guard and registration layouts are new. These are **incompatible new deployments with new deterministic addresses**, not upgrades to deployed V1/V2. Do not reuse old transaction BOCs, addresses, receipts or fingerprints. Existing project APIs continue to expose the existing V2 profile; this PR does not silently relabel them VNext or publish VNext signing.

## External evidence boundary and emergency recovery

1. Existing STON.fi deposit/refund messages and captured Router, Pool, LPAccount and LP wallet bytecode execute in Sandbox. These are compatibility simulations, not live Testnet deployment or canonical receipts. Router administration/upgrades can change behavior and reserves; the approved trust model still requires independent review of exact versions and upgrade policy.
2. An authenticated LP wallet notification with immutable contributor/operation payload can credit the existing Locker under its existing checks. A self-transfer probe can establish a **custody floor only**, not exact first issuance, full balance, migration attribution or withdrawn amount. It cannot repair a missing first notification for arbitrary partial/time-limited locks. No signature is accepted as a substitute.
3. Existing off-chain raw receipt checks verify exact message edges, code, account-state deltas and claim records; inclusion is relative to a reference. They are not validator-quorum finality or messages that Locker can consume. The small frozen-state correction preserves those labels.
4. The foreign wallet's standard excess is not final recipient delivery evidence. An immediate authentic bounce of the original transfer may restore a request; a downstream bounce or absent notification may not. Full withdrawal delivery/recovery stays pending until a contract-authenticatable mechanism exists.
5. The smallest architecture candidates for external review are an immutable on-chain proof consumer anchored to authenticated TON validator/state history, or a genuinely compatible external wallet/pool extension that emits correlated authenticated final outcomes. Neither exists in this package. A wrapper cannot add a receipt to an unmodified foreign wallet merely by naming a callback.
6. Emergency buyer recovery is **not implemented as a payout**. `get_emergency_recovery_vnext` returns a conservative local no-dispatch reserve check and a separate zero authorization flag. `recovery-liability-model-vnext.js` only tests pro-rata arithmetic, fee preservation, duplicate cumulative credit, rounding and dispatch/solvency exclusions. It is not a ledger, receipt verifier or financial message builder. Timeout, even seven days, is insufficient. Exact atomic token redemption, in-flight exclusion, gas funding and exactly-once payout must be independently designed and reviewed before any payment path is added.

The authority can withhold permissions, choose permitted minimum-LP terms, or be compromised; these remain availability/slippage governance risks for a future activation. It cannot alone originate a Curve/Migrator-authenticated state query, change immutable LP terms, credit LP, create refund evidence, withdraw principal, bypass permanent locks or fabricate canonical finality. Review must validate those properties over every legacy handler, not only the new signature check.
