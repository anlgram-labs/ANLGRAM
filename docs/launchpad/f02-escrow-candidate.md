# F-02 escrow candidate — unverified, never deploy or fund

This is a source-level custody and recovery candidate, not a completed migration engine. It has not been compiled or run. Sending real assets risks permanent loss. No production contract imports it; Gate 414 and the existing financial configuration are unchanged. Version 3 changes StateInit and is incompatible with prior versions; there is no upgrade path.

## Identity and accounting

`minter-contract/scripts/f02-escrow-candidate.js` builds StateInit from the code cell, a nonzero operation ID, controller address, Jetton master and wallet code, with empty ledgers and history dictionaries. Different configuration tuples yield different addresses; operation IDs are not globally registered and identical tuples yield the same address. The creator must independently authenticate the controller, master, and exact wallet code and verify that its initial data is canonical. The on-chain code derives the escrow's wallet from its own address, that master and wallet code. This derivation assumes the pinned wallet implementation and master really use the repository's wallet StateInit layout; it is not a verification of a foreign master.

Each asset has available, pending, delivered, next sequence, pending sequence, and authenticated received principal. The contract checks `available + pending + delivered == received` whenever a ledger is read or written. This checks internal accounting only; it does not independently measure wallet balances or distinguish receipts returned from a DEX. The imported `f02-recovery-ledger.fc` limits each asset to one outgoing transfer and never reuses a sequence. TON principal and Jettons are distinct; caller-supplied TON funds gas, not Jetton principal. Recovery uses `raw_reserve` and sends with mode 1; storage fees, action failure and low-balance behavior still need actual TVM tests. History dictionaries grow with deposits, and their storage/gas bounds require review. There is no operation-wide terminal state.

## Entrypoints

All private opcodes use a 64-bit operation ID after the opcode. Controller-only requests must match the StateInit controller and operation ID.

* `0x46323001` deposit TON: positive principal, supplied with at least 0.05 TON additional value and a unique `uint64` deposit nonce before the amount. This adds a field to the version 1 wire format. Reused nonces are rejected. Credits only that principal.
* `0x7362d09c` Jetton notification: accepts positive amounts from the derived wallet, with the operation ID and configured controller as the notification's original sender. It rejects repeat serialized messages by full message hash rather than treating a shared query ID as a duplicate. This relies on actual TON message identity and wallet correctness; validate it with real traces. Wallet authentication is only as sound as the master/code assumptions above.
* `0x46323002` recover TON: controller gives next sequence and amount; reserves principal, then emits bounceable `0x46323005` with operation, sequence and amount to that same controller. A matching bounce records non-delivery but does not automatically restore principal, because fees may reduce the returned TON.
* `0x46323006` restore bounced TON: controller identifies the still-pending sequence and supplies gas. The contract requires a matching recorded bounce and a real TON balance sufficient to cover available plus all pending principal and the 0.05 TON reserve; the controller must make up any fee shortfall. It then restores the full pending amount to available and consumes the bounce record. This balance/gas calculation is untested and needs fee and action-phase review.
* `0x46323004` acknowledge TON: controller attests to exact sequence and amount, moving pending to delivered, provided no bounce was recorded. This is an explicit trusted-recipient attestation, not independent proof of delivery. It cannot safely be used to settle DEX liabilities.
* `0x46323003` recover Jetton: reserves principal and sends `0x414e5301` to the configured **ANLGRAM opt-in settlement wallet**, addressed to the controller, with caller-funded gas. Its `0x414e5304` receipt is accepted only from the derived wallet with the exact outstanding sequence and amount: status 2 records delivery to the recipient wallet; status 3 restores available principal after that wallet reports it restored custody. A bounced request alone does not restore availability.
* `0x46323007` queries and `0x46323008` retries the same pending Jetton request. A retry preserves the exact wallet owner ID, amount and destination. This relies on the opt-in wallet's persistent deduplication and retry protocol. A missing record, missing receipt or timeout never releases principal. No generic excess, notification, timeout or third-party message confirms delivery.

Messages accepted from outside these paths do not add accounted principal. An empty-body TON message is accepted but unaccounted. Jettons from another origin, with another query ID, without notification, or sent by an unsupported wallet may be held without an available recovery path. If no valid wallet outcome arrives, or the wallet code does not implement the opt-in protocol, principal stays pending. TON bounce recovery is blocked if no authenticated bounce arrives or the controller cannot cover the balance/reserve shortfall. **This candidate can trap assets and must not be funded.**

## STON.fi and validation gaps

The offline helper exposes the existing `stonfi-lp-v2-wire` builder and refund builder for message inspection. The candidate does not dispatch either message, verify the STON.fi router/LPAccount, credit partial or delayed refunds, deliver LP to Locker V3, or implement closure. The existing builder's Locker V2 payload and its destination assumptions must be reviewed before reuse with Locker V3. An LP notification, empty account, or timeout cannot establish that asynchronous obligations closed. A possible alternative is an explicitly trusted reconciliation authority, whose assumptions need separate approval; no such mechanism is implemented.

`f02-escrow-candidate.test.js` prepares tests for deterministic address separation, controller and operation authentication, multiple TON deposits, bounced TON restoration, gas checks, duplicate and wrong-amount acknowledgments, pending queries, repeat requests, derived-wallet checks and outgoing TON/Jetton message shape. One case is designed to compile the repository's actual minter and wallet, transfer two Jetton deposits, execute a partial recovery and check wallet balances and settlement receipt transactions. Other injected wallet messages exercise parsing only. All tests are unexecuted. A compliant isolated environment must first compile and run them, then use actual wallet bytecode and traces to test action failure, gas exhaustion, real downstream bounce, delayed return, partial refund, duplicate/reordered messages, asset conservation, Locker failures, and all requested STON.fi cases. Any observed failure requires fixing and rerunning before security review.

In that verified offline environment, with pinned dependencies pre-staged read-only, the intended command is `node --test tests/settlement-runtime/f02-escrow-candidate.test.js`. The test compiles the contract and its fixtures in memory; it does not produce a verified persistent artifact or code-cell hash. No dependency installation is authorized during the run.
