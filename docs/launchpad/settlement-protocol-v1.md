# Authenticated Jetton settlement v1 — development protocol

Status: local TVM/Sandbox evidence only. Separate opt-in wallet code, not an
upgrade or a claim of TEP-wide receipt compatibility. Standard Jetton handlers
remain available. The unchanged original wallet stays in the repository.

## Wire messages

All custom bodies start with a uint32 opcode. IDs are uint64, amounts are Coins,
addresses use MsgAddress. These opcodes belong to ANLGRAM, not STON.fi.

| Opcode | Remaining body | Authenticated meaning |
| --- | --- | --- |
| `0x414e5301` transfer | owner ID, amount, destination owner, response owner, Maybe custom payload, forward Coins, Either payload | Wallet owner initiates once; response must be own owner |
| `0x414e5302` internal | wire ID, amount, source owner, forward Coins, Either payload | Peer wallet derived from source owner, master and identical wallet code |
| `0x414e5303` ack | wire ID, amount | Expected recipient wallet reports persistent credit |
| `0x414e5304` receipt | owner ID, wire ID, amount, uint2 status | Sender wallet reports delivered=2 or restored-after-bounce=3 |
| `0x414e5305` retry | owner ID | Caller funds ledger query/replay; no new entitlement |
| `0x414e5306` query | wire ID | Return ack only if authenticated incoming record exists |
| `0x414e5307` not-seen | owner ID | Sender wallet has no operation; never a failure receipt |

Outgoing `wire ID = cur_lt()` is generated by the sender wallet. An authenticated
owner operation ID cannot create a second transfer. A repeated identical request
replays a final receipt or queries the peer. A different amount/destination using
that owner ID is rejected. Incoming duplicate ID/peer records do not credit twice.

The actual bounced internal message authenticates the recorded peer, wire ID and
amount. Only a pending transfer restores tokens; a finalized operation cannot
restore again. Recipient ack and bounced failure cannot change a finalized
outcome. A missing ack, owner notification or excess does not prove failure.
Query bounces are not transfer failures.

## Persistent state and Curve accounting

Wallet initial data remains balance/owner/master/wallet-code reference. Once used,
an optional dictionary follows this header. Keys are 256-bit cell hashes of:

- `OWNQ` (`0x4f574e51`) + owner ID: wire ID index.
- `OUTG` (`0x4f555447`) + wire ID: uint2 status, owner ID, amount, peer wallet.
- `INCM` (`0x494e434d`) + peer address + wire ID: credited amount.

Curve root storage shape remains unchanged. Its existing dictionary adds completed
operation tombstones. It accepts receipts only from its exact wallet and only
when stored wallet code matches the generated hash pin. Initialization cannot
replace that genesis code. Matching pending amount/ID is consumed once; completed
duplicates must match the stored beneficiary/amount/wire/status.

A failed buy delivery leaves the paid purchase economically booked. Restored
Jettons back a beneficiary's token escrow, not a TON refund and not new sale
inventory. Claims use new operation IDs; a failed claim restores one escrow.
This prevents simultaneous tokens, TON refunds and resale of the same inventory.

## Gas and failure recovery

Existing buy overhead 0.04 TON, wallet attachment 0.035 TON and 1 nanoTON
notification remain unchanged. No price, 1% fee, 1B supply, 80/20 split or 500 TON
threshold changes. Wallet checks funding before token debit/credit; token transfer
actions must succeed or bounce. Receipt and owner-notification action errors may
be skipped to preserve credited/restored tokens and the persistent outcome.
Receipt gas cannot roll back custody. Query/retry regenerates missing receipts.

Retries are explicitly funded by the caller and reserve prior Curve balance.
Known-wallet Curve retries accept at least 0.02 TON. An authenticated not-seen
response needs at least 0.04 TON arriving at Curve to resend the same owner ID
with 0.035 TON to its wallet; tests use a 0.06 TON retry. These are local evidence,
not future fee guarantees. Never resend an accepted internal transfer or refund
because time elapsed. If a recipient is frozen, wait for actual authenticated
bounce restoration. If neither custody nor delivery is proven, retain pending.

The native TON paid into frozen accounts can remain in their balances. There is
no universal sweep/recovery for it. Permanent operation records need rent/scale
review. Higher network fees may require a separately approved gas policy.

## LP authentication and DEX boundaries

The separate guard sends actual TEP-89 `provide_wallet_address` / authenticated
`take_wallet_address` messages and Router `getter_pool_address` (`0x2993ade0`).
It binds two configured distinct masters, their Router-owned wallets, that pair's
Pool and the Pool's guard-owned LP wallet. Each phase checks source, nonce, owner
and message structure. Admin retry generates a fresh nonce. Phase 5 means address
binding only. `is_migration_authorized()` always returns zero. No withdraw, burn
or upgrade handler exists. Old `set_lp_wallet` messages are rejected.

Source of the actual foreign interfaces:
[STON.fi Router v2](https://docs.ston.fi/developer-section/dex/smart-contracts/v2/router),
[STON.fi Pool v2](https://docs.ston.fi/developer-section/dex/smart-contracts/v2/pool).
Foreign code identity, upgrade authority and balance/custody are additional trust
requirements. A TEP-89 reply alone cannot prove these. New-protocol Curve dispatch
and LP finalization reject 414 pending that work; legacy mode is not made safe by
this gate and must remain disabled in production.

The real-code DEX test separately preloads local project custody and executes
captured Router/pTON/Pool/LP contracts. It verifies 500 pTON + 200M Jettons in the
Pool, 316227766015836 LP units held by the guard-owned wallet, and 1001 minimum LP
units excluded from that holding. Unauthorized transfer and guard withdrawal fail.
These exact figures are fixture evidence, not a general DEX quote or a live lock.
The guard still refuses migration authorization. Partial deposits, LP-account
refund recovery and final Curve reconciliation are unfinished.

## Reproduction

From the isolated development checkout:

```powershell
node scripts/run-local-regressions.js
npm test --prefix tests/settlement-runtime
node minter-contract/test-bonding-curve-math.js
npm test --prefix minter-contract
node --test minter-contract/test-deploy-launchpad-testnet.js minter-contract/test-deploy-launchpad-testnet-exec.js minter-contract/test-supervised-execution-engine.js
```

From `minter-contract`, run `node compile-settlement-wallet.js --check`,
`node compile-bonding-curve.js --check`, `node compile-lp-auth-guard.js --check`
and `node compile-migration-router.js --check`. New compiler writes require wallet
first, then Curve (generated wallet hash pin), then guard and migration.
Use existing dependencies without installing through the shared E: junction.
