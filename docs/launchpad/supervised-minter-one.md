## Implemented

A single, separately labeled Testnet transaction panel was added to the existing isolated preparation interface. The normal connection bootstrap still cannot initiate financial requests. An owner click prepares fresh authenticated account/fee observations only. A different explicit acknowledgement and click is required to request Tonkeeper's native confirmation. No automatic signature request, retry, step#2, generic creation, trading, distribution, migration or Mainnet capability is enabled.

MINTER_TX1_PREPARATION is a finite owner-authorized preparation scope stored in Pages only: exact origin, candidate hash, V5 operator, minter destination,0.10TON attachment and0.12TON policy; configured for20minutes during this supervised session. Missing, changed or expired scope fails closed. It is not blanket financial authorization. Proof must match the fixed Testnet V5 operator, exact domain and unexpired challenge.

The server's prepare route rejects all caller transaction parameters, checks the lifetime operation lock before provider calls, and uses fresh authenticated account and exact invalid-zero-signature emulation observations. The existing complete-trace verifier was moved without changing its financial assertions into lib/v5-minter-trace.js and is shared by CLI and Worker. Source/bytecode and StateInit identities remain unchanged. Simulated message body hash, source balance, both deployed-state code/data hashes, seqno0->1, exact one internal deployment, fees and reserve conservation must all pass. The first external request also initializes the currently uninitialized V5 wallet. No extra internal deployment is added.

An exact fingerprint/deadline/trace/state approval snapshot is stored in the existing FinancialOperation SQLite namespace, without claiming the financial attempt. The existing claim route then requires that exact snapshot, fresh state, unexpired proof and scope, <=60second quote age, <=120second message validity and unchanged parameters. The atomic claim checks that the latest prepared fingerprint still matches. Any later preparation after a claim is rejected. There is no lock reset or retry endpoint. The UI distinguishes a wallet response from actual blockchain confirmation.
